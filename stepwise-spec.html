Stepwise

A practice space for data structures and algorithms where you write a solution and watch it run, one step at a time, drawn the way you would sketch it on a whiteboard.

Step 6 of 6 · “nums[5] is 11. Found it.”
Working name: StepwiseStatus: draft v0.1Date: 27 Oct 2026

Summary

Learners who think in pictures struggle with DSA because the material arrives as code and math notation, while understanding comes from seeing state change. Existing tools split the job: LeetCode-style sites give you problems and a pass/fail verdict, and visualizers such as VisuAlgo or Python Tutor show either canned animations or generic box-and-arrow memory diagrams.

Stepwise joins the two. A learner picks a problem, writes a solution, and presses Walk through. Their own code runs in the browser, every step is recorded, and the system detects what the data is (a grid, an array with two pointers, a linked list, a tree) and draws it that way. Each step gets one plain-English sentence. When a test fails, Stepwise jumps to the step where things went wrong.

The MVP is Python-only, runs fully in the browser, ships with 30 original problems and six visual views, and needs no account to start.

The interface is built with kbui, the in-house React component library. Anything Stepwise needs that kbui lacks is added to kbui rather than copied into the product. Building on kbui lists what already fits, the 20 gaps, and the order to close them in.

Problem

What learners run into

  • The work is invisible. A loop runs 40 times in a blink. The learner sees only the final output, so the cause of a wrong answer stays hidden.
  • Notation is a barrier. Σ, big-O and index arithmetic describe loops in a second language that many self-taught learners never learned.
  • Debuggers don't fit the job. A debugger lists i = 3, j = 7. A learner needs to see i and j as arrows on the array.
  • Visualizers are disconnected from practice. Watching a canned BFS animation is different from understanding why your BFS visits a cell twice.

Jobs to be done

  • When my answer is wrong, show me the exact moment my code did something I didn't expect.
  • When I read a solution I don't understand, let me watch it run on a small input.
  • When I learn a new pattern (two pointers, BFS, DP), show me what it looks like so I recognize it next time.

Goals and metrics

Goals

  • Make the effect of every line of a learner's code visible in a form that matches how DSA is taught.
  • Keep the interface simple enough that a first-time visitor completes a walkthrough within 60 seconds, with no signup.
  • Feel fast and calm: instant stepping, smooth motion, no flicker while typing.

Non-goals for MVP

  • Competing with LeetCode on problem count. 30 well-chosen problems beat 3,000 with no visuals.
  • Contests, rankings or social feeds.
  • Languages other than Python (JS/TS in v1, others in v2).
  • A full IDE. No files, no packages, no terminal.
  • Mobile code editing. Phones get read-and-step mode.

Product principles

  1. Three screens, one primary action each. Library: pick. Workspace: walk through. Walk mode: step. If a feature needs a fourth screen, it waits.
  2. One step, one moment. The highlighted line, the picture, the variables and the sentence always describe the same instant. Nothing lags behind.
  3. Only what changed moves. Motion directs the eye. Everything that didn't change in this step stays perfectly still.
  4. Never go blank. Broken code keeps the last good picture on screen, dimmed, with a quiet badge. Learners mid-thought shouldn't lose their place.
  5. Draw it like a teacher would. Pointers are labeled arrows, grids are grids, trees are trees. The generic memory diagram is a fallback, not the default.
  6. Words beside pictures. Every step has one plain sentence. No jargon that the problem itself didn't introduce.
  7. The learner can always override. Any automatic choice (view, speed, input) is one click to change and stays changed.

Functional requirements (MVP)

Each requirement lists the acceptance checks that close it.

FR-1 Problem library

  • Shows each problem's title, pattern tag, difficulty and the learner's status (new, attempted, solved).
  • Filter by pattern and difficulty; search by title. Filters persist across visits.
  • Accept: list renders from local cache in under 100 ms; keyboard users can reach and open any problem with Tab and Enter.

FR-2 Problem statement

  • Statement, examples and constraints in a drawer that opens over the editor. Closed by default once the learner has opened it once.
  • Accept: drawer toggles with P; focus moves into it and returns to the editor on close.

FR-3 Editor

  • Python syntax highlighting, bracket matching, indentation, basic completion of names in scope.
  • Starter code per problem. The draft autosaves locally after 1 s of idle time.
  • Accept: typing latency under 16 ms with a 200-line file; reloading the page restores the draft.

FR-4 Run tests

  • Runs all visible test cases off the main thread and shows pass or fail per case, with expected and actual values.
  • Accept: a correct solution for any MVP problem reports results in under 500 ms after the runtime is warm.

FR-5 Walk through

  • Runs the selected test case with tracing on and switches the workspace into walk mode. Defaults to the first failing case, else the first case.
  • Records at most 5,000 steps. Past that, the walkthrough keeps what it has and says so.
  • Accept: trace of 5,000 steps is ready in under 400 ms; the walk opens at step 1 with the line, picture and sentence in sync.

FR-6 Step controls

  • Previous, play/pause, next, scrubber, jump to start and end, speed (0.5×, 1×, 2×, 4×).
  • Step over and step out for function calls; “next time this line runs” by clicking a line number.
  • Accept: each step renders within one frame (under 8 ms of main-thread work); scrubbing across 5,000 steps never drops below 50 fps.

FR-7 Code and state sync

  • Current line highlighted. A compact variables panel lists locals; values that changed this step pulse once.
  • Call stack shown when depth is above 1.
  • Accept: at every step, the highlighted line, the views and the variable panel come from the same snapshot (checked by an automated test that compares them).

FR-8 Automatic views

  • The detector assigns a view to each relevant variable and lays out at most three primary views. A badge names what it found (“Grid + BFS”).
  • The learner can switch any variable's view or pin it. Pins persist per problem.
  • Accept: on the reference solution of every MVP problem, the detector picks the intended primary view (golden tests).

FR-9 Narration

  • One sentence per step, generated from templates keyed on the kind of event (compare, assign, append, pop, call, return, branch taken).
  • Accept: no step shows an empty sentence; screen readers announce it through a polite live region.

FR-10 Jump to failure

  • On an exception, the timeline marks the step and the walk opens there. On a wrong answer, it opens at the final return and offers “Watch from the start”.
  • Accept: both cases covered by end-to-end tests on seeded bugs.

FR-11 Live mode

  • When on, edits re-run the current test case 400 ms after typing stops. If the code doesn't parse or crashes, the last good walkthrough stays, dimmed, with a “Showing last working run” badge.
  • After a re-run, the walk tries to stay at the same line and loop iteration.
  • Accept: no blank frames during 60 s of continuous typing; main-thread long tasks stay under 50 ms.

FR-12 Progress and accounts

  • Everything works without an account. Signing in (email link or GitHub) syncs drafts, status and pins.
  • Accept: a learner who signs in after solving 3 problems keeps all 3 marked solved.

FR-13 Runaway code

  • Step cap, 3 s wall-clock limit and memory limit. The Stop button interrupts within 100 ms.
  • The message names the likely cause: “Stopped after 5,000 steps. The loop on line 4 may never end.”
  • Accept: while True: pass never freezes the tab.

Microcopy rules

  • Narration uses the learner's own variable names: “lo moves to 4”, not “the left pointer moves”.
  • Present tense, active voice, one sentence, under 90 characters.
  • Errors say what happened and what to try. No apologies, no raw tracebacks unless the learner expands them.

  • Easing: --kb-motion-easing-standard for state changes, -enter and -exit for items appearing and leaving. No bounce or overshoot in views.

  • Stillness: the editor never animates layout, and nothing moves while the learner is typing.

Accessibility

  • Target WCAG 2.2 AA across the product, checked with automated axe tests in CI and a manual screen-reader pass (VoiceOver, NVDA) each release.
  • Every action works from the keyboard, with a visible focus ring. Touch targets at least 44 px on phones, 24 px minimum elsewhere.
  • Narration goes to a polite live region, so screen-reader users hear each step.
  • Each view has a table alternative (“Show as table”) that renders the same state as an accessible HTML table, with pointer positions as columns.
  • No meaning by color alone (see the visual language table). Palette verified with protanopia, deuteranopia and tritanopia simulation.
  • Text scales to 200% without losing content; views reflow or scroll inside their own panel.
  • Respects prefers-reduced-motion, prefers-contrast and prefers-color-scheme, each also settable in the app.

Visualization system

The system has three layers that only talk through two data formats. Adding a language touches only the first layer; adding a view touches only the third.

Runner → Trace→Detector → View spec→Renderer

Trace

A language-neutral record of every step: the line, the call stack, the locals, and a heap of objects with stable ids so aliases (two names for one list) draw as one object. Full schema in the appendix.

  • Storage: a full snapshot every 64 steps plus small deltas between them. Seeking to any step costs one snapshot plus at most 63 deltas.
  • Large values: lists over 1,000 items keep a window around the indexes the code touched, plus the length.
  • Events: each step is tagged with what happened (compare, assign, call, return, append, pop, branch), derived from the syntax node on that line. Narration and markers use these tags.

Detection

Three signals vote for each variable's view:

  1. Runtime shape from the values themselves. A list of equal-length lists is a grid; an object whose only self-typed field is next is a linked list.
  2. Code roles from syntax queries with tree-sitter. In grid[r][c], r and c are the cursor on grid; in nums[lo], lo is a pointer on nums.
  3. Problem context from the problem's tags (“grid-bfs”, “two-pointer”). For pasted problems in v1, an LLM proposes the tags once and the result is cached.

Score = shape × 0.5 + roles × 0.3 + context × 0.2, and a learner pin overrides everything. Below a confidence of 0.6 the variable gets the generic view. A layout pass then picks up to three primary views; the rest stay in the variables panel.

Building on kbui

kbui is a React 19 component library on Base UI 1.9, with design tokens and plain CSS. This analysis uses its latest main branch (v0.7.0): 21 components, token-only styling enforced by bun run check, light and dark themes, forced-colors checks, and a Storybook accessibility scan on every story.

Rule carried over from kbui. Every component a product screen needs and kbui lacks is added to kbui, not copied into the product. Parts that only make sense in Stepwise, such as the visual views, stay in Stepwise's repository. Stepwise is a good source for kbui's planned catalog work, which already lists Tabs, Table, EmptyState and a Split layout.

What changes in this spec

  • Framework: React 19 with React Router 7 replaces SvelteKit, because kbui is React-only.
  • Components: kbui on Base UI replaces Bits UI.
  • Styling: kbui tokens and plain CSS. Stepwise's own CSS reads only --kb-* semantic, scale and component tokens.
  • Look: kbui's default theme replaces the violet palette. Visualization colors come from new --kb-viz-* tokens.
  • Motion: kbui transitions for the interface, GSAP only for views, both timed by kbui's motion tokens.
  • Landing: the demo walkthrough waits for a press, since nothing in kbui animates on its own.

Changes across kbui

  • Color separation. kbui's rust accent (#b4462b) and danger (#a33444) are close in hue, and so are info teal (#276c69) and success green (#356747). The viz tokens must stay apart: blue for current, teal for visited, amber for changed, danger plus an icon for error. Check them with color-vision simulation and 3:1 non-text contrast in both themes.
  • Motion tokens. Add motion.duration.layout (about 320 ms) for tree and graph relayout and a viz.pulse-duration component token (400 ms). Everything else maps to the existing fast, base and slow durations.
  • Forced colors. kbui already checks Button under forced colors. The viz tokens need system-color fallbacks (Highlight for current, Mark for changed, GrayText for discarded) and patterns in place of fills.
  • Touch targets. The dock uses sm controls on desktop. At phone width they need at least 44 px, through a media rule or a touch size.
  • Keyboard rule. Toolbar uses arrow keys to move focus. Global ← and → stepping applies only when focus is on the page, a view or the timeline. The shortcut hook (G15) enforces this.
  • Isolation headers. Stepwise serves COOP and COEP for Pyodide. kbui ships its CSS inside the package, so it loads from the same origin. Confirm in CI that every page renders under require-corp.

Stays in Stepwise

The array, grid, linked list, tree, hash map and call tree views; the playback engine and trace store; narration; the detector; the runner workers; and the CodeMirror integration. Views draw plain SVG or canvas styled with --kb-viz-* tokens and never render a kbui component per cell or per step, which keeps each step under the 8 ms budget. A view moves into kbui only if a second product needs it.

How the work flows

  • Each addition meets kbui's contract before release: anatomy line, story, test, screenshot assertion, accessibility scan in light and dark, token-only CSS, and an entry in kbui's feature register.
  • During development Stepwise installs kbui by path; CI installs a pinned release tarball. kbui keeps all three packages on one version.
  • Group kbui releases by Stepwise phase: one release with G1–G7 before Phase 1, one with G8–G15 and G20 before the MVP beta, and later releases for v1 items.
  • A temporary component inside Stepwise is allowed only with a ticket to move it into kbui within the same phase.
  • The local kbui checkout is on an older feature branch, 55 commits behind main. Update it before starting.

Techniques

  • Start loading Pyodide on the library page when the browser is idle; cache it with a service worker so later visits skip the download.
  • Load CodeMirror language packs and tree-sitter grammars on demand.
  • Snapshot plus delta storage makes seeking cheap; precompute view geometry for each snapshot in the worker.
  • Batch DOM writes to one per animation frame; animate only transform and opacity.
  • Switch a view from SVG to PixiJS above its element threshold; window long arrays around active pointers.
  • Debounce live mode; cancel stale runs so only the newest result renders.
  • Performance budgets are enforced in CI with Lighthouse CI and a step-render benchmark.

Safety and security

  • Learner code runs in a worker with no DOM access. The Pyodide build ships without its network helpers, and the worker's content security policy blocks connect-src.
  • Hard limits: step cap, wall-clock timeout, interrupt flag, and worker restart if memory passes the cap.
  • v2 server runners: one container per run, no network, CPU and memory quotas, read-only filesystem, destroyed after use. Rate-limited per user.
  • LLM output is data only: validated against the view-spec schema, never run as code, cached by problem hash.
  • Shared links contain a server-stored id, never code or personal data in the URL.
  • Privacy: code stays on the device unless the learner signs in or shares. Analytics never captures code contents.
  • Content: every problem statement is written in-house. Classic problems are fine as ideas, but no copied statements, numbering or names from other platforms.

Testing and quality

  • Golden traces: each problem's reference solution produces a trace that is checked into the repository; changes to the tracer must keep them identical or update them on purpose.
  • Detector tests: golden view choices for every problem, plus property tests that generate random grids, lists and trees and check the detector classifies them.
  • Seeded bug suite: five common wrong solutions per problem (off-by-one, missed visited check, wrong base case) that must produce a useful jump-to-failure.
  • Visual regression: Playwright screenshots of each view at fixed steps, light and dark, three widths.
  • Accessibility: axe on every screen in CI; keyboard-only end-to-end test of the core loop.
  • Performance: benchmark that scrubs 5,000 steps and fails the build if frame time regresses past budget.

Appendix

Trace schema

type Trace = {
  language: "python" | "javascript" | "typescript" | string;
  source: string;
  steps: Step[];            // stored as snapshots every 64 steps + deltas
  truncated?: "steps" | "time" | "memory";
};

type Step = {
  i: number;
  line: number;
  event: "line" | "call" | "return" | "exception";
  tags: ("compare" | "assign" | "append" | "pop" | "branch" | "index")[];
  stack: Frame[];           // innermost last
  heap: Record<HeapId, HeapObj>;
  stdout?: string;
  exception?: { type: string; message: string };
};

type Frame = { fn: string; line: number; locals: Record<string, Value> };

type Value =
  | { kind: "prim"; type: "int" | "float" | "str" | "bool" | "none"; v: unknown }
  | { kind: "ref"; id: HeapId };

type HeapObj =
  | { kind: "list" | "tuple" | "set" | "deque"; items: Value[]; len: number; window?: [number, number] }
  | { kind: "dict"; entries: [Value, Value][] }
  | { kind: "object"; cls: string; fields: Record<string, Value> };

View spec schema

type ViewSpec = {
  confidence: number;               // 0..1
  badge: string;                    // "Grid + BFS"
  views: View[];                    // at most 3 primary
};

type View =
  | { type: "array"; bind: string; pointers: string[]; window?: string[] }
  | { type: "grid"; bind: string; cursor?: [string, string]; overlays?: Overlay[] }
  | { type: "linkedList"; head: string; pointers: string[] }
  | { type: "tree"; root: string; pointers: string[] }
  | { type: "hashMap"; bind: string }
  | { type: "callTree"; fn: string }
  | { type: "graph"; bind: string; frontier?: string; visited?: string }
  | { type: "dpTable"; bind: string }
  | { type: "generic"; bind: string };

type Overlay = { set: string; style: "visited" | "frontier" | "path" };
